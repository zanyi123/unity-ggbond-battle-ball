# 新子项目/新功能开发技能

## 触发条件

当用户提出以下类型需求时，本技能激活：

- 添加新功能、新系统
- 开发全新玩法模块
- 创建新的游戏机制
- 重构某个子系统为独立模块
- 添加 UI 系统优化
- 开发技能系统、装备系统等扩展
- 开发独立的 demo 或原型

## 核心原则

### 模块化优先
- 新功能必须先作为独立模块开发
- 独立 demo 验证后再接入主项目
- 不直接在主项目堆代码

### 修改范围控制
- 每轮最多修改 1-3 个文件
- 修改前必须说明计划
- 不得擅自修改公共接口
- 不得擅自修改节点名、信号名、输入映射

### 测试驱动
- 每个功能必须有测试编号
- bug 维修前先判断根因
- 每轮只修一个根因
- 输出复测清单

### UI 独立面板规范
- 创建新独立面板时，背景必须不透明（alpha = 1.0 或 ≥ 0.98）
- 必须设置 `set_anchors_preset(Control.PRESET_FULL_RECT)` 铺满全屏
- 必须设置 `mouse_filter = Control.MOUSE_FILTER_STOP` 拦截鼠标，防止点到背后内容
- 避免背景透出底层界面导致视觉混乱

## 工作流程

```
用户提出需求
  ↓
判断：是否需要独立模块？
  ├─ 否 → 直接实现（修改范围≤3文件）
  └─ 是 → 进入模块化开发流程
         ↓
     模块边界定义
         ↓
     独立 demo 规划
         ↓
     第一阶段最小目标
         ↓
     demo 实现 + 验证
         ↓
     接入主项目（如需要）
```

### 判断是否需要独立模块

**需要独立模块的情况：**
- 新增完整系统（技能系统、装备系统、招募系统等）
- 重构某子系统为独立可测试模块
- 需要复杂 UI + 逻辑的多层系统
- 可独立运行验证的功能

**不需要独立模块的情况：**
- 简单的单文件逻辑修改
- 现有模块内部的小优化
- bug 修复（一般不触发模块化）

## 修改计划输出格式

```md
## 本轮目标

[目标描述]

## 准备修改的文件

1. `path/to/file1` - [修改原因]
2. `path/to/file2` - [修改原因]

## 不准备修改的文件

- [文件] - [不修改原因]

## 最小方案

[实现路径]

## 影响范围

[受影响的系统/功能]

## 下一步

[行动]
```

## 禁止事项

**不得在新功能阶段顺手完成：**
- UI 完整化
- 存档接入
- 主项目接入
- 大规模重构
- 额外玩法扩展
- 无关系统优化

## 信息不足时的行为

停止写代码，只输出：
1. 当前无法判断的原因
2. 需要补充的文件
3. 需要补充的节点树
4. 需要补充的报错
5. 用户从 Godot 哪里能找到这些信息
6. 补充后下一步会做什么

**不得：**
- 编造项目结构
- 假设节点存在
- 猜测完整实现代码
